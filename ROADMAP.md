# Roadmap

Що лишилося зробити. Історія змін — у [CHANGELOG.md](CHANGELOG.md).

## 1. Нормалізована колонка заголовка

Одна зміна, яка закриває дві проблеми одразу.

**Пошук не знаходить назв з діакритикою.** `-eu4 Lubeck` не знаходить `Lübeck`,
`-hoi4 Quebec` — `Québec`, `Grossbritannien` — `Reichskommissariat Großbritannien`,
а набраний з клавіатури апостроф не збігається з типографським у
`Abu Bakr II’s Ambition`. У базах 33 такі заголовки. Fuzzy-підказки ловлять
частину, але не всі.

**Індекси не працюють.** Розширити `normalize()` і перенести її в SQL через
`create_function()` не можна: SQLite не індексує власні функції, тож expression
index став би непридатним. Але й наявний expression index на
`LOWER(REPLACE(title,'_',' '))` **уже нічого не дає** — `WHERE ... LIKE
'%query%'` має провідний `%`, який жоден B-tree обслужити не може. Плани запиту
з індексом і без нього ідентичні (`SCAN Pages`), час теж; при цьому індекс
додавав ~217 КБ до `eu4.db`. Тому `scripts/add_search_indexes.py` видалено.

**Рішення:** додати `Pages.norm_title` (і `Redirects.norm_redirect_title`),
заповнювати в `scripts/import_wiki.py` через `normalize()`, індексувати
звичайним індексом. Тоді:

- нормалізація лишається **однією** функцією на Python — без паралельного
  SQL-виразу, що розходиться з нею;
- гілки `= :exact` і `LIKE :prefix` починають реально йти через індекс;
- гілка `LIKE :contains` усе одно сканує — це вже задача для FTS5.

Потрібна міграція для наявних баз (нова версія `scripts/add_search_indexes.py`,
яка додає колонку, заповнює її й індексує).

## 2. FTS5 для пошуку входжень

Коли баз стане більше або вони виростуть, `LIKE '%query%'` перестане бути
прийнятним. FTS5-таблиця, що будується разом з імпортом, — правильна відповідь.

## 3. Колонка `lang` недостовірна

В eu4 46 рядків позначені «Українська», але ведуть на англійські URL
(`/Absolutism`, `/Aachen`) — імпортер проставляв мову хибно. Пошук цю колонку не
читає, тож функціонально нешкідливо. Перезбирання через
`prop=langlinks` у MediaWiki API виправить дані.

## 4. Slash-команди для пошуку

Зараз на слешах лише `/admin`. Решта — префіксні, тобто залежать від
привілейованого інтенту `message_content`, який після 100 гільдій потребує
верифікації Discord. Перевести пошук на `app_commands` з автодоповненням назв
сторінок — і блокер зникає, і UX кращий.

## 5. Prometheus + Grafana

Зараз спостережуваність — це UptimeRobot, який б'є в `/health` і відповідає на
одне питання: живий чи ні (див. README → Моніторинг). Цього досить, щоб
дізнатися про падіння, і замало, щоб побачити деградацію: скільки пошуків на
день, які повертають нуль результатів, скільки часу займає аплоад на pdx.tools,
чи ростуть помилки бази.

Зробити як у `Find-Music-Bot` (`deploy/alerts.yml`, `deploy/grafana-dashboard.json`):

- `prometheus_client`, ендпоінт `/metrics` у наявному aiohttp-застосунку —
  окремий порт не потрібен;
- лічильники: пошуки за грою, порожні результати, ✅/❌ голоси, аплоади за
  результатом (успіх / дублікат / відмова API), помилки SQLite;
- гістограми: тривалість пошуку, тривалість аплоаду;
- алерти: сплеск порожніх результатів (ознака, що база застаріла), сплеск
  помилок аплоаду, відсутність будь-яких запитів за N годин.

Свідомо відкладено: Prometheus + Grafana — це ще два контейнери й том під дані
на машині, де бот займає ~100 МБ. Робити, коли зʼявиться друга інстанція або
реальні користувачі, чиї скарги треба буде підтверджувати цифрами.

## Дрібниці

- `paradox_bot/cogs/tools.py:70` — коментар згадує `temp/`, куди код більше не
  пише. Запис `temp/` у `.gitignore` варто лишити як оборонний.
- `aiohttp.BasicAuth` і параметр `auth=` у `pdx_tools.py` позначені як
  застарілі й зникнуть в aiohttp 4.0 — перейти на
  `headers={"Authorization": aiohttp.encode_basic_auth(...)}`.
